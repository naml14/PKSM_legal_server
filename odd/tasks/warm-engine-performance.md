# Motor caliente: bajar el tiempo de respuesta de la API

La API responde en ~1 s porque **levanta un motor nuevo en cada peticion** y el motor paga
~350 ms de arranque en frio de la pila PKHeX/ALM antes de hacer nada. El trabajo real de una
legalizacion son 1-70 ms.

## Specs

- **S1** — Peticion del usuario (verbatim): "ahora vamos por optimizaciones de rendimiento, así disminímos los tiempos de respuesta ya que mi VPS está físicamente en alemania".
- **S2** — Medido (sonda `tmp/startup`, ALM 26.10.18, .NET 10.0.403): el camino `legality` completo son ~345 ms, de los cuales **mgdb 24 ms + GetFromBytes 6 ms + el primer `LegalityAnalysis` 145 ms + el primer `la.Report()` 150 ms + el primer `JsonSerializer.Serialize` 19 ms**. En caliente (la segunda vez en el mismo proceso) el mismo analisis son **1 ms** y el reporte **0 ms**. El arranque de una app .NET minima son 63 ms y el motor entero 477 ms (`version`), de los que ~350 ms son `ALMVersion.Versions` (solo el comando `version`) y el resto la pila PKHeX/ALM.
- **S3** — El coste por peticion tiene que bajar de forma medible: el motor tiene que **reutilizar el proceso** para no pagar el arranque en frio en cada peticion. Requisito: el tiempo de la legalizacion de un fixture que hoy son ~480 ms medidos en frio tienen que ser el coste del trabajo real mas el coste de la llamada (objetivo: menos de la mitad).
- **S4** — El modo `serve` del motor: lee peticiones de la entrada estandar y escribe una respuesta por linea en la salida estandar, **reutilizando el proceso** (la pila PKHeX/ALM ya cargada). El contrato de la CLI (`version`, `summary`, `legality`, `legalize` y sus codigos de salida) **no cambia**: el modo `serve` es un comando mas y el modo de una sola peticion sigue igual.
- **S5** — La capa Go tiene que poder usar el motor caliente sin cambiar el contrato de las rutas v2 (`/api/v2/pksm/legality` y `/api/v2/pksm/legalize` devuelven exactamente lo mismo que hoy). Si el motor caliente no esta disponible, la API **cae al motor de una sola peticion** (el comportamiento de hoy) en vez de fallar.
- **S6** — Los modos que no necesitan los sprites (los de legalidad y de legalizacion) **no** los cargan: `Sprites.Init()` solo hace falta para el resumen.
- **S7** — Cuando no hay DSN de Sentry, el SDK **no** se inicializa (hoy se inicializa en cada peticion y cuesta ~28 ms).
- **S8** — No regresion: las 59 fixtures de `pokemons/` siguen legalizandose con el reporte vacio, los tests C# y Go siguen en verde y los veredictos de `tools/verify-baseline.txt` no cambian.
- **S9** — El modo `serve` no puede morir por una peticion invalida: una base64 que no es un Pokemon responde con el error correspondiente (y el proceso sigue vivo), como hoy responde el codigo de salida 2/3.

## Tasks

- **T1** (C#, `coreconsole/`) — El modo `serve`: el protocolo, el bucle, la captura de la salida de los handlers y el S7 (Sentry solo con DSN) y el S6 (sprites solo para el resumen). -> S4, S6, S7, S9
- **T2** (Go, `internal/utils/`, `internal/handlers/`) — El grupo de motores calientes en la capa Go, con la caida al motor de una sola peticion. -> S3, S5
- **T3** (C#, tests) — Tests del modo `serve`: el protocolo, una peticion invalida que no mata el proceso, dos peticiones seguidas y el resultado identico al de la CLI. -> S4, S9
- **T4** (Go, tests) — Tests del grupo de motores: la reutilizacion, la caida cuando el motor no arranca y el mismo contrato de las rutas. -> S5
- **T5** (parent, integracion) — La medida antes/despues con la API real, los dos arneses, la linea base y los commits por unidad de trabajo. -> S3, S8

## Log

- L1 (usuario): "ahora vamos por optimizaciones de rendimiento, así disminímos los tiempos de respuesta ya que mi VPS está físicamente en alemania"
- L2 (evidencia, sonda `tmp/startup`): el reparto del tiempo de una peticion es `mgdb 24 ms + GetFromBytes 6 ms + LegalityAnalysis 145 ms + la.Report() 150 ms + JsonSerializer 19 ms` en frio, y `1 ms + 0 ms + 0 ms` en caliente. El arranque en frio de la pila PKHeX/ALM es **el** coste dominante: ~350 ms por peticion que no dependen de la peticion.
- L3 (evidencia, sonda `tmp/startup`): `ALMVersion.Versions.AlmVersionCurrent` y `CoreVersionLatest` cuestan ~350 ms la primera vez (solo los usa el comando `version`, o sea el endpoint `/api/general/ping`); `EncounterEvent.RefreshMGDB` 24 ms; `Sprites.Init()` 4 ms; `SentrySdk.Init` 28 ms; el arbol de la CLI 12 ms; un `JsonSerializer.Serialize` de un POCO 26 ms.
- L4 (decision del padre): la optimizacion es **reutilizar el proceso del motor**, no recortes de codigo: el trabajo real es de 1-70 ms, asi que el techo del tiempo de respuesta lo pone el arranque en frio. Recortar el resto (Sentry, sprites, CLI) son 40 ms de 480 y no cambian el orden de magnitud.
- L5 (decision del padre): el modo `serve` no cambia el contrato de la CLI. La respuesta del protocolo lleva **la misma salida que imprime la CLI y su codigo de salida**, para que la capa Go siga interpretando el payload igual que hoy.
- L6 (decision del padre): la API cae al motor de una sola peticion si el caliente no esta disponible: una peticion que no se puede servir no puede ser un error 500 por una optimizacion.
- L7 (incidencia, entorno): no hay SDK de .NET en el `PATH` (solo el runtime 10.0.14); el SDK esta en `.dotnet10/` (10.0.403), que es lo que ya espera el `Makefile`.
- L8 (evidencia, PRODUCCION, 2026-11-09): medido contra el VPS (`https://electrondevnaml.dev/`, conexion persistente para quitar el handshake de la medida): el RTT desde aqui es de **180 ms** (la respuesta estatica de `kuma-ping` tarda 180 ms) y el handshake TLS inicial son **388 ms** (una vez por conexion). Los tiempos de servidor (mediana menos el RTT): `v2 legality` **~710 ms**, `v2 legalize` **~1128 ms**, `general/ping` (el comando `version` del motor) ~412 ms. Sin conexion persistente el `ping` llegaba a 2395 ms: la primera vez hay que leer el runtime .NET y las DLL de PKHeX del disco, y esa pagina cache Cold se paga en cada peticion nueva. Ese es el coste que el motor caliente elimina.
- L9 (T1 y T3, worker + padre): el motor tiene el comando `serve`. El padre reviso el diff y movio la clase `Serve` de `Program.cs` (que se comia 335 lineas) a `coreconsole/handlers/Serve.cs`, donde viven los demas handlers. El Pokemon que ALM regenera NO es determinista (PID aleatorio, ya antes de este cambio), asi que ese caso se compara sin el campo `pokemon`.
