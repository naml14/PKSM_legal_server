# PKSM v2 alias + correccion de 3 defectos del CoreAPI

Implementar las rutas `/api/v2/pksm/*` que la app 2ds/3ds PKSM espera, y corregir los tres defectos de contrato detectados al probar todos los endpoints con archivos `.pk9` reales.

Contexto: la API Go (FlagBrew/CoreAPI) corre en `output/app/` con `coreconsole` (C#) como motor de legalidad. El 2ds (192.168.0.210, UA `PKSM-curl/8.4.0`) hace `POST /api/v2/pksm/legality` y recibe **404**: esa ruta pertenece a `FlagBrew/local-gpss`, no a este repo.

## Specs

- **S1** — El 2ds llama a la ruta `"/api/v2/pksm/legality"` (cadena textual del usuario). Debe existir en este servidor y responder con el mismo formato que `FlagBrew/local-gpss`.
- **S2** — Contrato exacto de `local-gpss` (`internal/utils/pkhex.go` + `internal/handlers/legality/handler.go` de ese repo):
  - `POST /api/v2/pksm/legality` y `POST /api/v2/pksm/legalize`.
  - Cabecera `generation` **obligatoria**; cabecera `version` **obligatoria solo en legalize**. Si falta la cabecera requerida -> HTTP 400 `{"error":"version header is required"}` (texto literal de `local-gpss`).
  - Multipart con campo `pkmn`; limite de 2 MB.
  - Respuesta legality: `{"legal":<bool>,"report":[<string>]}`.
  - Respuesta legalize: `{"legal":<bool>,"success":<bool>,"ran":<bool>,"report":[<string>],"pokemon":<string|null>}`.
- **S3** — Defecto 1: falta el campo `pkmn`, el campo va vacio o el request no es multipart -> HTTP **400** con mensaje limpio, nunca 500 ni texto interno de Go. Hoy el servidor responde `500 {"error":"http: no such file"}` y `500 {"error":"request Content-Type isn't multipart/form-data"}`. Tamano de body > 1024 bytes -> 413 `{"error":"file too large"}` (se mantiene). Contenido que no es un Pokemon -> 400 con el cuerpo de error de coreconsole (se mantiene).
- **S4** — Defecto 2: `forced_generation` debe funcionar. Hoy `POST /api/legality/legalize` con `forced_generation=Gen9` responde **200 con el texto de ayuda de coreconsole** en vez de JSON. Causas: (a) coreconsole declara `--legalization-generation` como `Option<int?>` pero la API Go envia nombres (`Gen1`..`Gen9`, `Gen7b`, `Gen8a`, `Gen8b`, `MaxInvalid`, `None`, `SplitInvalid`) que no parsean como int; (b) `coreconsole/Program.cs` ignora el codigo de salida de `cli.Invoke(args)` y siempre sale con 0, asi que un error de parseo de la CLI se vuelve "exito" para la capa Go. Requisitos: (a) coreconsole debe aceptar los mismos nombres que ya envia la API Go; (b) un error de parseo de la CLI debe producir codigo de salida distinto de 0; (c) `POST /api/legality/legalize` con `forced_generation=Gen9` debe responder JSON, nunca texto de ayuda.
- **S5** — Defecto 3: legalizar un Pokemon ya legal responde hoy 200 con `{"error": "this pokemon is already legal!"}`. Debe responder codigo de error HTTP (400) con ese mismo cuerpo de error, tanto en la ruta legacy como en la v2.
- **S6** — No regresion: las rutas existentes (`GET /api/general/kuma-ping`, `GET /api/general/ping`, `POST /api/info`, `POST /api/legality/check`, `POST /api/legality/legalize`, `/.well-known/security.txt`, `/debug/pprof`) deben seguir respondiendo igual que hoy, salvo los cambios de S3 y S5. El binario de coreconsole debe seguir construyéndose con el SDK local del proyecto.
- **S7** — Fase 1 (reparar y reintentar, **automatico**): cuando ALM no puede legalizar un Pokemon porque sus datos bloquean la busqueda del encuentro de origen, el motor debe repararlos y reintentar. **La reparacion es automatica y del lado del servidor**: el usuario no toca el archivo, no usa el editor de PKSM y no reintenta a mano; el motor detecta el dato que bloquea, lo corrige sobre una copia, reintenta con ALM y devuelve el Pokemon legalizado con la lista de cambios (S9).
  - Fecha de encuentro invalida (año 1 o fecha imposible) -> una fecha plausible del juego destino de la generacion del archivo.
  - Movimiento con PP 0 -> el PP maximo del movimiento; los huecos de movimiento vacios se dejan para que ALM los rellene.
  - HT (entrenador que te entrego el Pokemon) ausente -> se copia el OT (nombre, genero, idioma).
  - El reintento se hace con la misma cadena de versiones por generacion (L16) y, si aun asi no sale, se pasa a S8.
- **S8** — Fase 2 (encuentro real mas cercano, **automatico**): si la reparacion no basta, el motor debe construir el Pokemon legal a partir de un **encuentro real** de la especie/nivel/version, conservando del Pokemon recibido lo que se pueda (especie, apodo, nivel, naturaleza, IVs/EVs, shiny, genero, objeto) y dejando el resto conforme al encuentro, de modo que el Pokemon siga siendo reconocible y ademas sea legal. La API de ALM 26.10.18 lo permite via `Legalizer.TryAPIConvert(ITrainerInfo, IBattleTemplate, PKM template, IEncounterable enc)`. Tambien es automatico: sin intervencion del usuario.
- **S9** — Transparencia: la respuesta de legalizacion debe incluir la **lista completa de cambios** aplicados al Pokemon de entrada (por ejemplo "met date 1/1/1 -> 2017-11-17", "move 1 PP 0 -> 35", "HT -> OT"). Si no se toco nada, la lista va vacia.
- **S10** — Arbol de decisiones por MENSAJE de ALM (mejora de S7/S8). La reparacion no puede ser "reparar todo y reconstruir de mas": debe ir al dato concreto que el mensaje de ALM senala, y el resultado debe cambiar lo minimo. Reglas:
  1. Se intenta ALM tal cual y se recogen los motivos del `report`.
  2. Cada motivo se clasifica y se aplica SOLO la reparacion que le corresponde:

     | Motivo de ALM | Que se toca | Que NO se toca |
     |---|---|---|
     | `Met Date is not a valid calendar date` | la fecha de encuentro -> fecha plausible del juego destino | lugar, nivel, movimientos |
     | `Invalid Move N: Invalid Move.` | solo ese movimiento (PP y/o ID) -> movimiento valido para especie/nivel | la fecha, el lugar, la habilidad |
     | `Hidden Ability mismatch for encounter type` | la ranura de habilidad -> una ranura valida de la especie | la fecha, el lugar, los movimientos |
     | `Mystery Gift cannot be received by this version` | la met location -> una location real de esa version | la fecha, los movimientos, la habilidad |
     | `HT Language is missing`, `Invalid Current handler value`, `Memory: Not cleared properly` | los datos del HT (nombre, idioma, memoria) | el resto |
     | `Unable to match an encounter from origin game` | el ORIGEN completo, y solo si las reparaciones anteriores no bastan | lo que ya sea valido y se pueda conservar |
     | `PID should be equal to EC!`, `PID-Nature mismatch`, `Should have at least 3 IVs = 31` | nada: los regenera ALM | todo lo demas |

  3. Tras una legalizacion **exitosa** se pasa un **restaurador minimo**: se intenta devolver al Pokemon el valor original de cada campo (fecha de encuentro, met location, met level, movimientos y PP, habilidad, HT, IVs/EVs, naturaleza, objeto) **mientras el Pokemon siga siendo legal**, y solo se reportan como cambios los que no se pudieron restaurar. Un Pokemon con una fecha de encuentro valida (p. ej. 10/4/2023) NO debe ver cambiada su fecha.
  4. La reconstruccion desde un encuentro real (S8) es el ULTIMO recurso y solo se usa si las reparaciones dirigidas no bastan.
- **S11** — Cobertura TOTAL de los motivos del check (criterio del usuario, 2026-11-07): "cuando mande a ese endpoint desde la 2ds internamente debe ajustar todo lo que el check ya avisó que está mal". Es decir, **ningun motivo que devuelve el check puede quedar sin resolver**: el Pokemon devuelto por `legalize` tiene que pasar el check con el reporte vacio (`["Legal!"]`). La prueba es `tools/verify-legalization.py`, que para cada Pokemon de `pokemons/` hace check -> legalize -> check del resultado y falla si queda algun motivo.
  Casos criterio: `0001 - Bulbasaur - 96132FF56EFC.pk7` (3 motivos) y `0002 ★ - Ivysaur - 38262FF56EFC.pk7` (7 motivos). El Ivysaur es el caso limite: sus motivos son `Invalid Move 1: Invalid Move.`, `Invalid: Unable to match an encounter from origin game.`, `Invalid: SID16 should be 0.`, `Invalid: Met Date is not a valid calendar date.`, `Invalid: Current handler cannot be the OT.`, `Invalid: GeoLocation Memory: Memories should be present.` e `Invalid: Event OT Friendship does not match base friendship.`; ademas su `version` es **Gold** (Gen 2) dentro de un `.pk7` (Gen 7), por lo que no hay ningun encuentro posible en la generacion destino. Requisitos:
  - Todo motivo del check debe tener una reparacion dirigida en el arbol, o una accion de "ALM lo regenera" que de verdad lo resuelva.
  - Si la `version` del Pokemon no pertenece a la generacion destino (el caso Gold en un `.pk7`), hay que corregirla a una version de la generacion destino **antes** de buscar el encuentro: es lo que en el Mew resolvio `Mystery Gift cannot be received by this version`.
  - Los motivos de HT/memoria que faltaban (`Current handler cannot be the OT`, `GeoLocation Memory: Memories should be present`, `Event OT Friendship does not match base friendship`) y el `SID16 should be 0` deben resolverse tambien.
  - El resultado debe seguir cambiando lo minimo (S10) y el `changes` debe seguir siendo el diff real.

- **S12** — Legalizar especies que no tienen encuentro en la generacion destino (criterio del usuario con 48 ejemplos, 2026-11-07): el usuario anadio 37 Pokemon mas a `pokemons/` y 37 de los 48 fallan con `Invalid: Unable to match an encounter from origin game.` y `pokemon: null`. Todos son de la misma familia sintetica (EC 2FF56EFC) y su problema es que la ESPECIE no tiene un encuentro salvaje en la generacion destino (Alola/SM-USUM): Pikachu, Gengar, Metapod, Butterfree, Beedrill, Kakuna, Clefairy, Clefable, Jigglypuff, Wigglytuff, Gloom, Vileplume, Venomoth, Nidoqueen, Nidoking, Hitmonlee, Hitmonchan, Jynx, Electabuzz, Magmar, Gyarados, Articuno, Zapdos, Moltres, Dragonite, Mewtwo, Ariados, Bellossom, Politoed, Espeon, Umbreon, Unown, Ursaring, Piloswine. Requisitos:
  1. La busqueda de encuentro debe **probar tambien otros niveles** del Pokemon (hoy `LowestLegalLevel` solo se aplica en la ruta de pre-evolucion): si a nivel 1 no hay encuentro pero a nivel 5 si, el Pokemon se legaliza a ese nivel (y el `changes` lo dice).
  2. Si la especie no tiene encuentro salvaje en ninguna version de la generacion, hay que buscar el encuentro **de regalo o evento** (la base de datos de regalos se carga con `EncounterEvent.RefreshMGDB`), ajustando la met location a una valida para esa version.
  3. Si tampoco hay encuentro (ni salvaje, ni de regalo, ni de forma previa en la generacion), el Pokemon **no puede ser legal en esa generacion**: la respuesta lo dice de forma explicita y accionable (que especie es, en que generacion si existe y por que no se puede aqui), nunca un `pokemon: null` mudo. Cambiar la generacion destino es un ULTIMO recurso que **no** se hace por defecto: la generacion la fija el formato del archivo.
  4. Se mantiene todo lo anterior: generacion = formato del archivo, versiones de la mas nueva a la mas vieja, restaurador minimo, `changes` = diff real, y el Pokemon devuelto tiene que pasar el check con reporte vacio.

- **S13** — El juego de origen es irrelevante (decision del usuario, 2026-11-07): "La gracia es que sea un pokemon legal, no importa el juego en el que se encontro". El motor ya no queda encerrado en la generacion del archivo: si en ella (y en todas sus versiones) no hay ningun encuentro para la especie, se sigue buscando en las demas generaciones. Requisitos:
  1. Orden de busqueda: primero la generacion del archivo (formato del `.pk7`/`.pk9`), con todas sus versiones base y el barrido de niveles; si no sale nada, las demas generaciones de la mas nueva a la mas vieja (Gen9, Gen8, Gen7, Gen6, Gen5, Gen4, Gen3, Gen2, Gen1), con sus versiones y sus niveles.
  2. Cuando el Pokemon legalizado venga de otra generacion, el `changes` lo dice de forma explicita (por ejemplo `generation Gen7 -> Gen6`) y la respuesta indica en que generacion quedo.
  3. El mensaje de "imposible" queda reservado para el caso en que la especie **no tiene ningun encuentro de ninguna clase** (salvaje, regalo, evento, estatico o forma previa) en **ninguna** generacion.
  4. **La busqueda tiene que caber en el timeout de la API** (30 s en `http.go`): hay que poner un presupuesto de tiempo total y un tope de intentos, y si se agotan, responder con el motivo (no un fallo mudo). El barrido de niveles 1..100 por version es la parte lenta: el limite debe estar acotado y documentado.
  5. No cambia el comportamiento de los Pokemon que ya legalizan en su generacion (mismos `changes`), ni el reporte de `legality` ni el de `summary`.
